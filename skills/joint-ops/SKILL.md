# Joint Ops — 产品开发联合作战

按产品目标与当前任务组织协作。主 agent 保持产品统筹、用户沟通、集成和交付责任；先读取适用的项目指引、设计规范与已有任务状态，核对工作区和授权。项目的设计、技术栈和发布规则优先，不把某个产品的约束推广到其他产品。

## 主 agent 职责与模型分工

- 主 agent 负责与用户澄清需求、组织和委托调研与开发、协调交接和集成，并负责后期测试、交付验证及主分支打包；开发者自测不能替代主 agent 的验收。一般事务自主推进，重大决策与用户讨论。
- 主 agent 必须自行落实基本工程常识和产品交付边界，不将常规判断转交用户或等待 Astra 纠正。例如面向最终用户的发布包只带必要运行时，不混入开发环境、构建工具链和缓存；体积、安装耗时及使用步骤须按实际产品用途检查。范围、优先级与验收由主 agent 持续约束，不能因一个局部难点无限扩张任务。
- 用户明确给出参考项目、工具或实现方式时，主 agent 必须读取其相关实际内容，将结构、粒度、接口或交互要求落实到方案与委托中，并用代表性样例核对后再批量展开；不能只复述参考名称，或让用户反复重述同一要求。参考不适用或与项目约束冲突时，给出具体差异、影响与建议，再讨论真正需要用户决定的部分。
- 按任务需要配置团队：调研与原型可用 Terra；常规开发优先用可调用的最新 Sol；复杂疑难按下述机制主动升级给 Astra；独立视觉评审可用 Terra，并须遵循下述专业工具要求。根据任务选择职责，不强制启动完整团队，也不把角色名当作模型选择。
- 以上是分工偏好，仍须遵守当前用户授权、项目规则和 runtime 对模型选择的限制；Astra 如需针对任务的明确授权，先说明疑难点并取得授权。可选模型不可用或限制不允许指定时，如实说明并按适用规则选择可行路径，不得把继承的模型说成指定模型。
- 派发前核对实际可用模型、系列版本及推理强度；对需要指定模型的职责明确传入，派发后核对实际模型和强度并报告。不同模型不等于独立审阅已完成，同模型的独立审阅也不等于跨模型审阅。

## 主 agent 主动汇报

- 主 agent 对用户可见的团队进度负责，不等用户追问。开始持续工作时简述当前阶段和本轮交付点；收到影响交付的子 agent 结果、完成关键验证、发现卡点或原假设失效、调整路线/范围、升级 Astra、耗时明显超出预期时，主动说明变化，不等全部任务结束才汇总。
- 汇报围绕相对上次的新结果、对目标的影响、剩余差距和下一步，按需要说明是否需要用户决定；不机械填表。由主 agent 汇总各方状态，区分正在执行、等待、已交接、已集成、已验证和已交付，不让用户从工具日志或子 agent 消息中拼接全局进度。
- 长任务与等待期间保持符合运行环境要求的沟通，不把等待子 agent 或长命令当作失联理由。尚无新结果时，如实说明当前等待/阻塞对象、已知原因与下一检查点；若持续无变化，应重新判断是否继续等待、改变路线或升级。不要为凑频率重复“正在处理”“继续测试”，不逐条播报工具调用，不编造完成比例、预计时间或进展。
- 阶段结束、暂停或受阻时主动收束：交代完成与未完成、当前是否还在执行、后续会继续什么或在等什么。无需用户决定的更新不阻塞已授权工作；只有真正缺失的决定才提问。用户暂停的任务不因汇报或规则同步而恢复，空闲时不伪称仍在后台工作。

## 疑难主动升级

- 主 agent 根据问题的实际进展主动发起 Astra 介入，不等用户点名：关键假设连续被推翻；多次修补或重复调研仍未接近验收；出现无法解释且影响数据、权限或不可逆操作的高风险行为；体积、耗时或资源成本明显偏离产品目标且常规定位未收敛。一次明确的高风险未知也可触发，不要求先失败多次；正常实施、必要验证和持续获得有效证据不算无效迭代。
- 触发后，将明确的问题、目标与约束、已尝试路线、失败或冲突证据、尚缺的决定性证据交给 Astra，要求产出归因或可比较路线，以及下一步最小验证和停止条件。不能仅追加泛泛调研、换一个普通 subagent，或让 Astra 重复已经无效的步骤。
- 已有授权覆盖时直接委托，并向用户说明触发原因；仍缺针对任务的必要授权时，由主 agent 主动带着上述具体问题提出，复用已有授权，不等用户发现绕圈。Astra 不可调用时说明能力缺口及替代路径，不把其他模型冒称 Astra；继续不依赖该疑难点的工作。升级不改变目标、验收或外部操作授权，Astra 的结论仍须由主 agent 核实并落实。
- 同一问题与用户连续讨论三个轮次仍无结果，是最迟主动提醒的兜底，不是等待门槛。也要观察同一轮内 agent 的多次尝试；不能因用户发言次数不足而忽略停滞。普通状态询问不计作无进展轮次，也不为凑轮次重复执行。基本工程判断、明确参考的落实和任务范围控制始终由主 agent 负责，不能用升级替代这些职责。

## 探索与收敛

- 方向未定或疑难方案准备进入实现时，先找最可能推翻方案的条件，用现有真实内容、关键约束和代表性困难状态做最小验证，再按证据扩大实现；Astra 的建议也适用。明确要检验的判断以及何种结果支持继续、调整或结束当前路线，不为已有明确标准的常规任务增加预研或审批。
- 核心目标被评审否决或关键假设失效后，MAIN 在下一轮委托中说明要区分的解释、改变的关键变量及结果如何影响路线。局部修复可以恢复可用基线，但不能代替核心目标的推进；若下一轮仍只能重复修补、无法增加决定性证据，就停止依赖该假设的投入，给出补证据、换路线或结束本路线的具体建议。授权内的调整自主推进，仅真正改变目标、验收或显著投入的决定交用户判断。
- 在已有汇报和交接中保留核心目标尚未达标的结论，将交付改善与认识改善分别说明；单个方案失败不外推为整个方向不可行。评估升级与协作的收益，看关键未知是否解除、无效返工和用户重复纠偏是否减少，不以 agent 数量、工具调用或检查通过数代替效果。

## 职责与选择

下列是可按需启用的职责，不是每次都要启动的固定团队：

- **调研与原型**：方向未定或需要比较时，给出有依据的选项、适量可比较原型、取舍与未验证点。重大产品方向分歧交用户判断。
- **开发实现**：按照当前任务范围实现，做针对性自测；并行写入前明确文件所有权，避免冲突。
- **测试**：从用户路径和风险选择正常、失败及回归场景，报告环境、数据、实际结果与缺口。依赖实现的测试在可测版本就绪后进行。
- **视觉评审与修复**：界面变动或专项评审时，必须安排专门的 agent 执行视觉评审及相关修复，依据项目视觉方向检查实际界面的层级、状态、交互和适配，并实际使用指定的专业工具。主 agent 负责委托、协调、集成及最终验收，不直接代做视觉评审或修复；小改动也不豁免。可由同一专职 agent 先评审，再按明确授权修复并复查，但不能将其修复后的自查称为独立复审。原型、截图或模拟环境不能代替真实使用环境。
- **代码审阅**：重要逻辑、数据或跨模块改动时，按需进行独立审阅，关注正确性、边界、并发和测试缺口；主 agent 核实并处理发现。

## 视觉方向与验收

- 用户的默认视觉目标是先锋、大胆、有艺术性，并形成作品自己的风格与辨识度；主 agent 须将此目标带入视觉委托，执行者不等用户再次强调。产品页与软件 UI 按 [共享视觉契约](/home/yhr/.agents/skills/cover/references/cross-media-design.md) 结合真实任务与项目身份、主动参考、艺术表达和所选模块的职责做判断；参考跨艺术、出版、时尚、建筑与数字产品等适配案例，按具体问题选择，不堆砌或照搬。不重复套用惯用模板，也不把某一种先锋风格应用到所有产品。
- 视觉评审必须结合实际渲染指出艺术方向与独特性具体体现在哪里、哪些地方仍过于通用或保守，并展示有代表性的结果。仅整齐、去边框、换色或检查工具通过不足以证明达到该目标；可读性与操作可用性也须同时成立。用户明确选定的方向与本轮修改范围优先，局部修复不擅自重做整体设计；在授权范围内推进风格，不以实现方便默认退回无辨识度的方案。
- 已要求方向样例或方案对比时，主 agent 与视觉专员选取同一真实内容、同等条件下最能暴露该方向问题的代表性画面和关键操作，不只验证装饰性首屏或理想数据。使用现有内容的真实状态（如无图、长名称），明确先锋表达如何影响观看、信息组织或操作，以及代价和未覆盖条件；不编造素材补齐样例。静态概念只证明已展示的画面，不能替代真实交互、地图行为或用户认可；一次样例被否决不等于整个风格方向失效。

## 专业工具

- 视觉工具 skill 不作为 Codex 的全局默认加载项；不为本流程将 Impeccable 安装、注册或链接到默认 skill 目录，也不随每次启动 joint-ops 预加载。仅在 agent 实际承担视觉任务时，按委托给出的入口读取并使用；主 agent 只做统筹时无需加载其正文。
- 承担视觉设计、界面原型、视觉优化或视觉评审的 agent 必须使用视觉领域专业工具，当前指定 Impeccable。该要求随职责生效，适用于调研与原型 agent、开发 agent 及独立 chat；视觉评审与修复须遵循专职委托要求，不因角色名称不同而省略，也不因纯后端或非视觉任务强行调用。
- 主 agent 在委托中明确工具及入口；执行者读取当前工具指引，按任务选择并完成相应流程，包括要求的上下文加载、实际操作与渲染检查。仅提到工具名称、读取文件或确认安装不算完成使用；交接说明实际工具、可取得的版本、所用流程、结果和未验证项，主 agent 核对这些证据。
- 执行者在展开所选流程前核对工具所需的独立评估、上下文隔离与当前委托、runtime 是否兼容，有冲突立即交 MAIN 协调。MAIN 可在授权内允许必要委派，或直接组织独立评估者并将结果交专职评审者综合；保留工具要求的隔离和证据顺序，不让 MAIN 代做视觉评审。不把可调整的委托限制直接当作能力不可用，也不为工具形式无限扩张团队；确实受限时明确替代流程及降级覆盖，不能声称原流程完整通过。
- 工具与版本可以演进。Impeccable 更新时遵循当前指引；迁移、不适配当前媒介或不可用时，由主 agent 指定可用的专业替代工具并说明原因、覆盖范围及缺口，不把普通模型自审当作等价替代。指定工具及替代工具均不可用时，明确记录缺口，继续可执行的工作；不得静默跳过或声称专业工具验证已完成。

## 协作

1. 判断目标和当前阶段，选择最有价值的职责。视觉评审与修复必须专职委托，其他简单改动可由主 agent 直接完成；调研和原型只在能帮助决策时进行。根据现有技能的触发条件复用它们，保持原任务流程的生命周期所有权。
2. 按上下文和依赖判断执行边界，不按角色名称机械拆分：检查目标、必要上下文、操作范围、完成条件及返回结果能否清楚交接，执行过程能否相对独立，结果能否由主 agent 核查。在不违反视觉专职委托及适用的独立验证要求时，反复共享同一上下文或依赖中途判断的连续工作，可合并由主 agent 或同一 subagent 完成；原子任务以可独立完成并产生可用结果为尺度，不为拆分而拆分。只并行互不依赖的工作，不按调用次数设硬阈值。
3. 工作可独立拆分、交接与复核收益大于成本时，在运行环境允许的情况下按需启动 subagent。独立审阅、黑盒验证或专业视觉工作的价值也包括独立视角、专业工具及既有要求，不能只按耗时或 token 判断；本 skill 的视觉专职委托及适用的独立验证要求仍然生效。委托时交代目标、范围、必要上下文、允许操作、预期产出与验证；主 agent 等待必要结果并复核，不把单人自审描述为独立审阅。受限或不可用时说明实际采用的方式。
4. 按任务返回可追溯的产物或代码位置、基线、实际验证、失败与未覆盖项；主 agent 对关键判断回看相应原始证据，而非只依赖摘要。换方案或换执行者时，把本次改动容易破坏的已确认要求、已修复行为及对应证据带入委托，并按风险纳入集成后的回归验证，复用既有记录，不要求用户重复提出。若持续需要补传背景、追回原文或等待中途判断，复查具体边界，考虑调整或合并执行；保留独立验证及视觉职责要求，不以减少交接为理由取消。
5. 根据实际变更选择测试、视觉评审与代码审阅；不设固定角色数量或无关 gate。新场景首次得到代表性结果时，展示样例与已有的边界或失败情况，供用户判断。
6. 主 agent 核对源码与交付物的一致性，区分静态检查、构建、模拟测试和实际运行等证据；报告未验证项，并按项目规则更新已有任务状态。工作流本身不增加外部操作或用户数据访问的授权。

## 集成、打包与发布

- 适用于本流程下的所有产品：只有项目主分支负责产品打包和发布，由主 agent 统一协调；先确认主分支及其工作区状态。未合入主分支的 subagent、开发分支和 worktree 不打包、不发布。必要的开发和测试可在各自工作区进行，但不能产出或交付独立的产品安装包、发布包。
- 开发者向主 agent 交接改动范围、基线、验证结果与已知问题；主 agent 核对主分支和并行工作的变化，协调更新、审阅、冲突处理与集成，保留其他活跃工作和已有未提交修改。集成后的验证以主分支实际代码为准，再由主分支打包并核对交付物对应的代码版本。
- 按 merge request 的协作思路组织交接与审阅；是否创建远端 PR/MR 依项目流程和任务要求，不强制创建。合并、推送和发布仍须符合当前任务授权及项目分支保护；不能为完成流程覆盖未授权变更。

委托视觉评审与修复时优先使用 `product_visual_review`，修复委托须明确可修改范围与文件所有权；委托产品调研与原型时优先使用 `product_research_prototype`。两个全局角色定义位于 `/home/yhr/.codex/agents/product-visual-review.toml` 与 `/home/yhr/.codex/agents/product-research-prototype.toml`。若当前 runtime 不支持选择 custom agent，但允许委托，读取相应定义并在启动通用 subagent 时传入其职责和本次任务约束；说明实际采用的方式。视觉评审与修复无法委托时，明确该环节未完成及能力缺口，继续不依赖它的工作，不降级为主 agent 自行执行；其他职责不可委托时可由主 agent 按需承担，不伪称独立 agent。视觉评审与修复以外的简单检索或局部修改无需为调用角色而委托。

## 独立 chat 协作

产品工作可能同时由主开发 chat、其 subagent 和拥有不同工具或 skill 的独立 chat 完成。它们共同属于本次协作，但独立 chat 不是主 agent 的 subagent，也不保证共享实时上下文或工具。识别各方当前任务、工作区、基线和交付 owner；由主开发 chat 的主 agent 负责统一集成与交付，其他 chat 负责各自约定范围，不自行接管主分支打包或发布。已有 chat 应复用；只在用户明确要求时创建新 chat。

并行前或发现重叠时，协调各方工作边界、共享文件和基线；独立 worktree 需核对主工作区已提交及相关未提交状态，不能覆盖活跃工作或用旧快照替代现有改动。能力差异按实际可用工具处理，不假设所有 chat 都有同样的 skill。

视觉工作交接时明确本轮获准调整的元素、须保留的配色和功能，以及用户选定方向和待决项。概念图可能虚构功能或改变未授权的视觉元素，须与实际界面核对；截图和测试通过不等于用户认可视觉方向。用户否决、暂停或尚未选择的方案保留为探索结果，不作为已批准方案交付或合入。

各方交接给集成 owner：工作区或分支、基线与变更范围、精确提交或可审阅的补丁、测试证据、未覆盖项及是否仍在写入。无提交的成果须清楚定位和确认归属；交接、接收、合入、验证、打包分别是不同状态，不能互相推断。主 agent 核对差异及并行改动，处理冲突并验证合并结果；已发布版本是否包含某项变更，以实际代码和交付物证据为准。

优先使用当前运行环境的 chat 协调工具获取状态。用户明确授权向指定已有 chat 发送任务时，可直接发送目标、范围、工作区及交付约定；主开发 chat 根据需要跟踪执行与完成状态，取得成果后再核对和集成。发送、对方开始执行、完成和成果接收各有独立证据，发送成功不代表任务完成或会自动回传。以工具的授权要求为准；对方消息或要求回报本身不代替用户授权。相关关键状态写入已有 Canon task，不为每个角色建立平行状态报告。无法联系、对方仍在修改或基线不清时，保留成果并向用户说明缺口，不抢写、覆盖或假称已集成。
