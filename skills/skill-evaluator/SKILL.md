# Skill Evaluator

当用户描述一段功能时，判断它**值不值得**封装成新 skill，还是直接用现有工具就能搞定。

## 为什么需要这个 skill

技能膨胀是 agent 系统的隐形杀手。每个新 skill 都会增加触发冲突、维护负担和认知成本。但反过来，该封装的不封装，又会导致重复劳动和流程不一致。这个 skill 在"过度封装"和"该封不封"之间找平衡。

## 触发方式

用户可能用以下方式表达需求：
- "我想实现一个功能，能自动..."
- "能不能做一个 skill，用来..."
- "这个要不要封装成 skill？"
- "需不需要创建一个 skill 来做..."
- "帮我评估一下这个功能"
- "这个功能用现有工具能做吗？"
- "我想自动化...，是不是该做个 skill？"

## 评估框架

从以下 5 个维度打分（1-5），每个维度一句话说明：

### 1. 现有覆盖度（Coverage）
- 5 = 已有 skill/tool 能 100% 覆盖，无需新建
- 3 = 现有工具能覆盖 60-80%，但需多步组合或手动调整
- 1 = 完全无覆盖，必须从零实现

**检查清单**：
- 扫描用户已安装的 skills（`~/.agents/skills/`、`~/.claude/skills/` 等），看是否有同名或同域 skill
- 检查现有 tools（Bash、Read、Edit、WebSearch、WebFetch、Agent、MCP tools）是否能直接完成
- 如果任务只是"读文件+改几行"，覆盖度 = 5；如果涉及跨文件状态管理、多轮决策，覆盖度可能 = 2

### 2. 复杂度（Complexity）
- 5 = 涉及多步骤、状态管理、跨文件操作、条件分支、外部 API 调用
- 3 = 涉及 3-5 个步骤，有一定上下文依赖
- 1 = 单步操作，或简单命令组合

**判断标准**：
- 是否需要记忆跨会话的状态？（是 → 高分）
- 是否需要根据中间结果做分支决策？（是 → 高分）
- 是否涉及多个工具的协调使用？（是 → 高分）

### 3. 使用频率（Frequency）
- 5 = 每天/每周多次使用
- 3 = 每月几次，或项目周期内反复使用
- 1 = 一次性任务，用完即抛

**判断依据**：
- 用户描述的语境（是日常工作流还是临时需求？）
- 如果用户说"每次都要手动做"，频率 = 5
- 如果用户说"就这次需要"，频率 = 1
- **校准参考**：
  - 频率 5：每天/每周多次（如"每次开会后"、"每天下班前"、"每个 PR 都要"）
  - 频率 4：每周 1-2 次或项目迭代中反复使用（如"每周同步一次"、"每个 sprint 末"）
  - 频率 3：每月几次（如"月度报告"、"月末汇总"）
  - 频率 2：项目里程碑或季度（如"发布前整理一次"、"Q4 复盘"）
  - 频率 1：一次性（如"这次迁移需要"、"临时处理一批数据"）

### 4. 触发清晰度（Trigger Clarity）
- 5 = 用户意图非常明确，可以通过清晰的关键词/描述准确匹配（如"生成周报"、"修复 bug"）
- 3 = 意图可识别，但需要一定上下文推断（如"把这段代码改好看点"可能对应多个 skill）
- 1 = 意图模糊，或任务本质上是工具链/环境配置（如编辑器设置、pre-commit hook），不适合由 agent 触发

**判断标准**：
- 能否用一句话概括这个 skill 的触发条件？
- 用户在不提"skill"的情况下，是否会自然地说出触发词？
- **重要**：如果任务本质上是编辑器/IDE/工具链层面的配置（如"保存时自动格式化"、"设置 git hook"），不适合由 agent 认知触发，触发清晰度 = 1-2。这类任务应通过工具原生能力解决，而非 skill。

### 5. 维护成本（Maintenance Cost）
- 5 = 依赖外部 API/格式/协议，容易过时，需要频繁更新
- 3 = 依赖稳定的外部系统，或内部代码逻辑
- 1 = 纯逻辑/流程，几乎不需要维护

## 决策矩阵

### 快速否决条件
以下任一条件满足时，无需深入评估其他维度，直接给出 🔴 **不创建**：
- **现有覆盖度 = 5/5**：已有工具/技能完全覆盖，无任何新建价值
- **触发清晰度 ≤ 2 且 复杂度 ≤ 2**：任务本质是工具链配置或单次简单操作，不适合 agent 触发

### 标准决策流程

通过 5 个维度的得分综合判断：

| 场景 | 结论 | 条件 |
|---|---|---|
| **强烈建议创建** | 🟢 创建新 skill | 现有覆盖度 ≤ 2 && 复杂度 ≥ 4 && 频率 ≥ 4 && 触发清晰度 ≥ 3 |
| **建议创建** | 🟡 创建新 skill | 现有覆盖度 ≤ 3 && 复杂度 ≥ 3 && 频率 ≥ 3 && 触发清晰度 ≥ 3 |
| **建议扩展现有 skill** | 🔵 扩展现有 skill | 现有覆盖度 = 3-4 && 某个已有 skill 可覆盖 60-80%，但缺少特定场景 |
| **不建议创建** | 🔴 不创建 | 现有覆盖度 = 5 || (现有覆盖度 ≥ 4 && 频率 ≤ 3) || (复杂度 ≤ 2 && 频率 ≤ 3) || 触发清晰度 ≤ 2 |
| **需更多信息** | ⚪ 待定 | 信息不足，无法判断频率或复杂度 |

## 输出格式

无论结论是什么，都按以下结构输出：

```markdown
## 评估结论：[创建 / 不创建 / 扩展现有 / 需更多信息]

### 评分
| 维度 | 得分 | 说明 |
|---|---|---|
| 现有覆盖度 | X/5 | ... |
| 复杂度 | X/5 | ... |
| 使用频率 | X/5 | ... |
| 触发清晰度 | X/5 | ... |
| 维护成本 | X/5 | ... |

### 理由
[2-3 句话说明为什么给出这个结论]

### 替代方案（如果不建议创建）
[具体说明用哪些现有 tools/skills 可以实现，给出操作步骤或命令示例]

### 如果决定创建
[给出触发词建议、skill 名称建议、核心逻辑概要]
```

## 示例

**用户输入**："我想实现一个功能，每次我打开新终端时自动显示当前 git 分支和最近的 commit 信息"

**评估过程**：
- 现有覆盖度：5/5 — Bash alias + git prompt 配置就能实现，无需 skill
- 复杂度：1/5 — 单行命令或 shell 配置
- 频率：5/5 — 每次开终端都用
- 触发清晰度：N/A — 这不是一个需要 agent 触发的任务
- 维护成本：1/5 — shell 配置一劳永逸

**结论**：🔴 不创建。建议用 `.bashrc`/`.zshrc` 中的 `PS1` 配置或 `starship`  prompt 工具。

---

**用户输入**："我想做一个 skill，能自动分析我的 conversation 历史，提取出我重复犯的错误模式，然后生成防错规则写入 .agent-state/rules/"

**评估过程**：
- 现有覆盖度：2/5 — `capture-mistake-rule` 能记录单次错误，但不能批量分析历史并归纳模式
- 复杂度：5/5 — 需要读取 conversation 文件、NLP 分析、模式归纳、规则生成、写入文件
- 频率：4/5 — 每周/每月运行一次，长期收益高
- 触发清晰度：4/5 — "分析我的错误模式"、"生成防错规则" 很清晰
- 维护成本：3/5 — 依赖 conversation 格式和规则文件格式

**结论**：🟢 创建新 skill。建议触发词："分析我的错误模式"、"生成防错规则"、"从 conversation 中提取教训"。
