# Deep Research

对给定技术方向进行结构化深度研究，基于本地代码仓库、本地知识库和外部信息源，
形成可执行的分析报告与推荐方案。

## 核心原则

### Start Wide, Then Narrow Down
研究必须从宽开始。即使主题看起来很简单，也必须先做一轮 codebase 广度扫描，
确认没有遗漏相关模块。窄化深入必须基于广度扫描的证据，而非先入为主的假设。

### 信息源优先级（不可颠倒）
```
用户知识库 Wiki（跨项目持久化笔记）> 本地代码（what exists）> 项目知识库（why/constraints）> 外部 web（supplement）
```
- Wiki 是"你过去已经想清楚的事"——有覆盖则外部搜索缩减，避免重复研究
- 外部最佳实践只有在不与 Wiki 结论和项目约束冲突时才推荐

## 为什么需要这个 skill

技术调研是日常开发的高频需求，但零散的信息收集（grep 几行代码、Google 搜几篇文章）
往往导致结论片面、遗漏本地约束、方案不可落地。这个 skill 强制按"先宽后窄、交叉验证、
可追溯"的结构化流程执行，确保研究报告既反映代码现状，又结合行业最佳实践，
最终给出在本地 context 下可执行的推荐方案。

## 触发方式

用户可能用以下方式表达需求：
- "帮我调研一下..."
- "做深度分析"
- "research on..." / "deep dive into..."
- "方案分析" / "技术预研"
- "分析一下这个方向"
- "研究一下怎么实现..."
- "这个技术在我们 codebase 里怎么落地？"

## 工作流总览

```
Phase 0: 确认研究范围 ──> Phase 1: 本地代码探索 ──> Phase 2: 本地知识库检索
  │                                                     ├─ 2.1 Wiki（跨项目，始终执行）
  │                                                     ├─ 2.2 项目 Agent State
  │                                                     ├─ 2.3 Agent Workspaces
  │                                                     └─ 2.4 提取约束与假设
  │                                                            │
  │                                                            ▼
Phase 5: 输出报告 <── Phase 4: 综合分析 <── Phase 3: 外部信息收集
```

## Phase 0: 确认研究范围

### 0.1 明确研究主题

与用户确认（如果用户描述模糊）：
1. **研究主题**：具体要解决什么问题？分析什么技术方向？
2. **范围边界**：限定在哪些模块/目录？排除哪些已知无关区域？
3. **输出深度**：粗略调研（1-2 小时工作量）还是深度分析（可涉及多轮迭代）？
4. **约束条件**：是否有硬性约束（如必须用某语言、某框架、兼容某版本）？

### 0.2 确定目标代码库

默认使用当前工作目录。如果用户指定了其他仓库：
```bash
cd <target_repo>
git status 2>/dev/null && git log --oneline -3
```

### 0.3 判断研究类型与 Effort Tier（决定后续 Phase 强度与 Guardrails）

根据研究主题判断 effort tier，调整后续 phase 的强度并应用对应 guardrails：

| Tier | 特征 | Phase 1 | Phase 3 | 典型耗时 | Guardrails |
|------|------|---------|---------|---------|------------|
| **Light** | 简单事实核查、单模块查询、已有明确答案 | 一次 grep/scan + 读取 1-2 个关键文件 | 可选，1 次快速搜索确认 | 5-15 分钟 | max 2 轮 thinking，max 1 次 web search，max 3 个文件读取，报告 ≤500 字 |
| **Medium** | 中等复杂度分析、跨 2-3 个模块 | 标准广度扫描 + 窄化深入 | 标准执行（2-3 步搜索） | 15-30 分钟 | max 4 轮 thinking，max 3 次 web search，max 10 个文件读取，报告 ≤2000 字 |
| **Deep** | 复杂架构分析、跨多个子系统、方案对比 | 标准执行 + **文档对比检查** | 深度执行（4-6 步搜索 + 多源交叉验证） | 30-60 分钟 | max 8 轮 thinking，max 6 次 web search，max 20 个文件读取，报告 ≤5000 字 |

**判断标准**（按优先级匹配）：

**Light（满足 1 项即可）：**
- 用户问的是"某个具体函数/配置/文件是做什么的"
- 答案可以在 1-2 个文件内找到
- 用户明确说"简要说明"、"快速回答"

**Deep（满足 2 项即为 deep）：**
- 研究涉及 3 个以上文件/模块
- 需要对比外部社区方案（如选型、架构评估）
- 需要提出改进建议或方案对比矩阵
- 用户描述中包含"完整分析"、"架构"、"可扩展性"、"改进建议"

**Medium（默认 tier）：**
- 不满足 light 也不满足 deep 的其他研究请求

> eval 数据：deep tier 研究中完整 Phase 结构带来 +71.4% 的断言通过率提升（vs without-skill baseline 61.5%）；light tier 中 Phase 3 可选策略显著节省 token 和时间。

## Phase 1: 本地代码探索（先宽后窄）

### 1.1 广度扫描（Broad Scan）

目标：快速了解 codebase 中与主题相关的全貌。

**行动**：
1. 用 Agent (explore) 或 Bash (find/grep) 扫描相关代码：
   ```bash
   # 按关键词搜索
   grep -riE "<keyword1|keyword2|keyword3>" --include="*.py" --include="*.js" --include="*.ts" --include="*.go" --include="*.rs" . 2>/dev/null | head -50
   # 按文件类型搜索
   find . -type f \( -name "*<topic>*" -o -name "*<related_concept>*" \) 2>/dev/null | head -30
   ```
2. 读取顶层架构文档（如果存在）：`README.md`、`ARCHITECTURE.md`、`CLAUDE.md`
3. 识别 3-5 个最相关的模块/目录

### 1.2 窄化深入（Narrow Down）

目标：选择最关键的 1-2 个模块深入理解。

**选择标准**（优先级排序）：
1. 与主题直接相关的核心实现文件
2. 已有类似模式的参考实现（可借鉴/复用）
3. 可能成为方案落地点的文件

**行动**：
1. 深度读取关键文件（Read 工具，完整内容）
2. 追溯调用链：该模块的入口在哪里？被谁调用？依赖什么？
3. 记录发现：代码结构、已有实现、设计模式、技术约束
4. **设计文档 vs 代码一致性检查**（深度型研究必须执行）：如果存在设计文档（`DESIGN.md`、`ARCHITECTURE.md`、`SPEC.md`、`README.md` 中的设计章节），对比文档描述与代码实际实现：
   - 文档中的算法/流程是否在代码中实际实现？
   - 代码中的行为是否被文档覆盖（是否有"代码做了但文档没写"的隐性逻辑）？
   - 标注不一致：[设计-代码一致 ✅] / [文档描述但代码未实现 ⚠️] / [代码实现但文档未覆盖 ❓]

> eval 数据：eval2-with 通过此检查发现了 DESIGN.md 的 active_time 算法在 report_renderer.py 中从未实现——这是 without-skill baseline 完全忽略的关键 gap。这类不一致往往是最有价值的研究发现，因为它说明"设计意图 vs 现实状态"的偏差。

### 1.3 迭代深化（可选）

如果深入后发现新方向（如"原来这个模块底层依赖了 X，而 X 正是研究主题的核心"），
回到 1.1 扩展搜索范围。使用 sequential-thinking（如果可用）或显式思考框架评估
是否值得扩展。

## Phase 2: 本地知识库检索

> **关键设计：三层知识体系。** 用户级知识库（Wiki）跨项目复用 → 项目 agent-state（当前 repo 上下文）→ agent-workspaces（项目设计文档）。三层逐级收窄，从通用到特定。

### 2.1 用户知识库（Wiki）— 始终执行

**无论当前工作目录在哪里，必须检索用户 Wiki 知识库。** Wiki 是跨项目的持久化个人知识管理系统，包含蒸馏后的技术笔记、概念页和深度研究报告。

**Wiki 根目录：** `/media/yhr/2T/files/wiki`

**检索步骤：**

1. **搜索相关笔记：**
   ```bash
   grep -rli "<keyword1\|keyword2\|keyword3>" /media/yhr/2T/files/wiki/queries/ /media/yhr/2T/files/wiki/concepts/ /media/yhr/2T/files/wiki/.research/ 2>/dev/null
   ```
2. **读取匹配的笔记**（优先 queries/，其次 concepts/，最后 .research/）
3. **检查 index.md** 确认是否有未命中但相关的条目：
   ```bash
   grep -i "<keyword>" /media/yhr/2T/files/wiki/index.md
   ```
4. **记录发现：** 已有笔记的结论、概念页的框架、前次研究的推荐方案

**Wiki 的定位：** 它是"你过去已经想清楚的事"，避免重复研究。如果 Wiki 中已有充分覆盖的笔记，Phase 3 外部搜索应相应缩减（减少重复劳动）。

### 2.2 项目 Agent 状态（当前 Repo）

按优先级读取当前项目的持久化知识：

| 优先级 | 文件 | 目的 |
|--------|------|------|
| 1 | `.agent-state/MEMORY.md` | 架构决策、已知问题、历史背景 |
| 2 | `.agent-state/conversations/*.md` | 历史会话中的相关讨论 |
| 3 | `.planning/conversations/*/` | 相关任务的 planning 文档 |
| 4 | `CLAUDE.md` / `AGENTS.md` | 项目级约束和风格指南 |
| 5 | `.agent-state/rules/mistakes.md` | 已知错误模式和防错规则 |

### 2.3 Agent Workspaces（项目设计文档 — 补充源）

如果当前项目有对应的 agent-workspace（通常在 `/media/yhr/2T/agent-workspaces/<project>/`），检查其中是否有相关的设计文档、架构决策记录或技术方案：

```bash
ls /media/yhr/2T/agent-workspaces/ 2>/dev/null
# 如果存在与当前项目同名的 workspace，读取其中的 CLAUDE.md、ARCHITECTURE.md 等
```

Agent workspaces 的定位是**项目级技术文档的长期存储**，与 repo 内的 .agent-state/（运行时状态）互补。Workspace 存的是"设计意图和架构决策"，.agent-state 存的是"当前会话的上下文和已知坑"。

### 2.4 提取约束与假设

记录以下信息：
- **架构决策**：为什么代码是这样设计的？
- **已知问题**：这个领域有什么已知坑？
- **技术约束**：版本锁定、兼容性要求、性能底线
- **历史尝试**：之前是否尝试过类似方案？结果如何？

## Phase 3: 外部信息收集

### 3.0 判断执行强度（基于 Phase 0.3 的 Effort Tier）

**Light tier**：Phase 3 **可选**：
- 如果本地代码+知识库已充分回答研究问题，只做 1 次快速 WebSearch 确认无遗漏
- 标记 `[外部信息: 本地信息充分，快速扫描确认无遗漏]` 后跳过 3.1-3.3
- 如果本地信息不充分，执行 3.1（1 次搜索）后进入 Phase 4

**Medium tier**：Phase 3 **标准执行**（3.1 → 3.2 → 3.3）：
- 2-3 步搜索（技术文档 + 社区讨论 + 案例参考）
- 必须读取至少 1 个外部页面（WebFetch）
- 记录外部约束

**Deep tier**：Phase 3 **深度执行**（3.1 → 3.2 → 3.3 + 多源交叉验证）：
- 4-6 步搜索，覆盖多个角度
- 必须读取至少 2 个外部页面
- 对冲突信息进行交叉验证（不同来源给出相反建议时，标记 🔴 [冲突] 并尝试解决）
- 记录外部约束和最新趋势

> eval 数据：light tier 中 Phase 3 可选策略避免了对简单查询的 token 浪费；deep tier 中完整 Phase 3 执行是跨模块研究的质量保障。

### 3.1 Web 搜索

目标：了解行业最佳实践、最新技术趋势、社区方案。

**搜索策略**：
1. **技术文档**：官方文档、RFC、设计文档
   ```
   WebSearch: "<技术名> best practices 2026" / "<技术名> official documentation"
   ```
2. **社区讨论**：GitHub issues、Stack Overflow、Reddit、Hacker News
   ```
   WebSearch: "<技术名> vs <竞品> performance comparison"
   ```
3. **案例参考**：知名开源项目的实现方式
   ```
   WebSearch: "<技术名> implementation example github"
   ```

### 3.2 深度读取

用 WebFetch 读取关键页面，提取：
- 核心概念和原理
- 最佳实践清单
- 已知陷阱和注意事项
- 性能/安全/可维护性权衡

### 3.3 记录外部约束

记录：
- 社区共识（"大家都这么做"）
- 反模式（"千万别这么做"）
- 最新趋势（2026 年的新方向）

## Phase 4: 综合分析

这是整个研究流程的核心决策点。借鉴 sequential-thinking 的方法论，
使用**迭代反思框架**处理多源信息的冲突、矛盾和不确定性。

### 4.1 检测 sequential-thinking 可用性

检查当前 agent 是否支持 sequential-thinking MCP：
- 如果 `mcp__sequential-thinking__sequentialthinking` 可用 → 使用工具化模式
- 如果不可用 → 使用显式思考框架（见 4.3）

### 4.2 工具化模式（有 sequential-thinking MCP）

在以下 4 个决策点调用 sequential-thinking：

**决策点 A：研究方向评估**
> Phase 1 发现多个相关模块，需要判断哪个方向最值得深入。
> 调用 sequential-thinking 评估各方向的 ROI（信息价值 vs 探索成本）。

**决策点 B：约束冲突分析**
> Phase 2 发现的历史约束与 Phase 3 收集的最佳实践冲突。
> 调用 sequential-thinking 分析约束优先级和可行性边界。

**决策点 C：方案对比评估**
> 形成多个候选方案，需要评估在本地 context 下的适用性。
> 调用 sequential-thinking 对每个方案做假设-验证循环。

**决策点 D：信息冲突解决**
> 本地代码实现与外部最佳实践矛盾，或不同外部来源给出相反建议。
> 调用 sequential-thinking 解决冲突、形成统一结论。

**调用方式**：
```
mcp__sequential-thinking__sequentialthinking:
  thought: "当前决策点：XX。已知信息：A、B、C。关键矛盾：X 与 Y 冲突。"
  thoughtNumber: 1
  totalThoughts: 5
  nextThoughtNeeded: true
```

### 4.3 显式思考框架（无 sequential-thinking MCP）

对于 Kimi、Pi、Hermes 等不支持 sequential-thinking MCP 的 agent，
使用以下文本化思考框架。这个框架是 sequential-thinking 核心机制的纯文本等价物：
（Claude Code 和 Codex 支持 sequential-thinking MCP，直接使用工具化模式）

#### 框架 1: 迭代深化（Iterative Deepening）

```
[思考步骤]
1. 先给出 BRIEF OVERVIEW（1-2 句话概括当前理解）
2. 识别当前理解中的 GAP（缺什么信息？哪里不确定？）
3. 决定 NARROW DOWN 方向（聚焦最重要的 1-2 个 gap）
4. 深入探索后，用 REVISED UNDERSTANDING 更新 overview
5. 重复 2-4 直到 gap 被充分填补或达到范围边界

[停止条件]
- 所有关键 gap 已填补 → 停止深化
- 达到用户指定的研究深度 → 停止
- 发现新 gap 但超出研究范围 → 记录为"未探索区域"
```

#### 框架 2: 修订机制（Revision Protocol）

```
[修订触发条件]
以下任一情况出现时，必须回头修订之前的结论：
□ 新发现的信息与之前结论直接矛盾
□ 之前基于的假设被证伪
□ 发现了之前遗漏的关键约束
□ 外部最佳实践与本地实现有根本冲突

[修订步骤]
1. 明确指出被修订的结论（原结论是什么？）
2. 说明触发修订的新信息（什么新证据？）
3. 给出修订后的结论（新结论是什么？）
4. 标注修订对后续分析的影响（哪些方案需要重新评估？）
```

#### 框架 3: 假设-验证循环（Hypothesis-Verification Loop）

```
[对每个候选方案执行]
1. 提出假设："方案 X 在本地可行，因为..."
2. 列出验证清单：
   □ 代码层面：本地是否有类似实现模式可复用？
   □ 约束层面：是否违反任何本地知识库记录的硬性约束？
   □ 兼容性层面：是否与现有依赖冲突？
   □ 维护层面：团队是否具备维护该方案的能力？
3. 逐条验证：用 Read/Bash 工具回到代码和文档确认
4. 标记验证结果：
   - ✅ 已确认（有代码/文档证据）
   - ⚠️ 推断（基于代码结构推断，无直接证据）
   - ❓ 未验证（需要更多信息）
5. 基于验证结果给出方案可行性评级
```

#### 框架 4: 分支探索（Branch Exploration）

```
[当存在多个研究方向时]
1. 列出所有可能的分支方向（最多 3 个）
2. 对每个分支做轻量探索（5-10 分钟）
3. 评估每个分支的信息 ROI：
   - 高 ROI：可能直接解决研究问题 → 深入
   - 中 ROI：提供有价值的背景信息 → 简要记录
   - 低 ROI：与研究主题关系较远 → 放弃
4. 选择 1-2 个高 ROI 分支深入，其他分支记录为"备选方向"
```

#### 框架 5: 不确定性标记（Uncertainty Annotation）

```
[在报告和中间结论中使用以下标记]
✅ [代码确认]     — 有直接的代码证据支持
📄 [文档确认]     — 有官方文档或项目文档支持
⚠️ [推断]         — 基于代码结构或模式推断，无直接证据
❓ [未验证]       — 需要进一步验证
🌐 [外部信息]     — 来自 web 搜索/文档，未在本地验证
🔴 [冲突]         — 与已有信息矛盾，需解决
```

### 4.4 方案对比矩阵

使用以下模板对比候选方案：

| 方案 | 优势 | 劣势 | 本地可行性 | 实施成本 | 维护成本 | 推荐度 |
|------|------|------|-----------|---------|---------|--------|
| A | ... | ... | ... | ... | ... | ... |
| B | ... | ... | ... | ... | ... | ... |

**可行性评估标准**：
- **高**：本地代码已具备实现基础，只需少量修改
- **中**：需要新建模块或引入新依赖，但技术路径清晰
- **低**：与现有架构冲突大，或需要大规模重构

### 4.5 引用验证（Citation Verification）

在输出最终报告前，回头检查所有关键声明的来源可靠性：

1. **列出关键断言**：从报告的研究发现、方案对比、推荐方案中提取所有具体断言
2. **验证来源**：
   - 本地代码证据 → ✅ [代码确认]
   - 本地知识库 → 📄 [文档确认]
   - 外部 web → 🌐 [外部信息]
   - 无直接来源 → ⚠️ [推断] 或 ❓ [未验证]
3. **风险评级**：
   - 高风险（影响方案可行性）的 [推断] 或 [未验证] 断言 → 补充验证或明确标注"基于推断，存在不确定性"
   - 低风险（背景信息）的 [推断] → 保留但标注不确定性
4. **生成来源置信度摘要**：高置信 / 中置信 / 低置信 的比例

**停止条件**：所有高风险断言已完成验证或明确标注；中低风险断言已标记。

## 关键约束

- **信息源优先级不可颠倒**：本地代码（现状）> 本地知识库（约束）> 外部 web（补充）。
  外部最佳实践只有在不与本地约束冲突时才推荐。
- **不可跳过 Phase 1**：即使主题看起来很简单，也必须至少做一轮 codebase 扫描。
  很多"显而易见的方案"在看了代码后会发现不可行。
- **报告必须可追溯**：每个结论都要标注来源，不允许"我认为..."这种无来源的断言。
- **跨 agent 兼容**：支持有 sequential-thinking MCP 和无 MCP 两种模式，
  确保在 Codex / Kimi / Pi / Hermes 等 runtime 上行为一致。
