# Taste Reference: 好/坏对照

以下示例来自真人 vs AI 对同一话题的写法。

---

## 1. 断言 vs 模糊

| ❌ 坏 | ✅ 好 |
|------|------|
| 本方案在实现层面具有较高的可扩展性 | 后续可以补 IR 和 Gray，不需要新增另一个 ToF actor |
| 该传感器能够满足产品侧的基本需求 | 你的产品目标是"可交付的 ToF 点云数据流"还是"完整物理 ToF 仿真"？前者匹配，后者需要另立需求 |
| 需要引入合理的抽象层以便后续扩展 | `output_components` 枚举当前只有一个值 `point_cloud`。补 IR/Gray 时加枚举值即可，不改 sensor class |

## 2. 具体 vs 抽象

| ❌ 坏 | ✅ 好 |
|------|------|
| 深度还原逻辑与已有 RGB-D 的实现保持一致 | 深度还原调用 `DepthImageEncoding::ConvertEncodedDepthToUint16Millimeters()` |
| 该传感器的默认分辨率为 240x156 | 默认分辨率为 240x156 |
| 点云输出格式为固定大小的浮点数组 | 点云 payload 固定为 `240 * 156 * 16 = 599040` bytes。每点 4 个 float32: x, y, z, i |
| 测试侧需要加强对 XX 的验证覆盖 | 测试评审建议把验收拆成五层：编译与注册 / Python API / Runtime 画面与点云 / DFS Proto / 数据一致性 |

## 3. 给人选择题 vs 给人派活

| ❌ 坏 | ✅ 好 |
|------|------|
| 建议产品侧确认是否需要 IR 和 Gray 输出 | 是否接受第一版只输出 `point_cloud`，IR/Gray 放入后续版本？ |
| 建议测试侧建立回归测试体系 | 普通 Depth、RGB-D、LiDAR 传感器不发生回归 |
| 需要产品明确 ToF 的业务定义 | 你的产品目标是什么？A. 可交付的 ToF 点云数据流 / B. 完整物理 ToF 仿真 / C. 算法直接使用的固定面阵点云 |

## 4. 一句定性 vs AI 三段论

| ❌ 坏 | ✅ 好 |
|------|------|
| 本方案新增了一个复合传感器类型，通过在一个 actor 内部署两个独立 capture component 的方式，实现了 RGB 图像与 Depth 图像在同一生命周期内的同步采集，从而在功能层面解决了用户需要手动管理两个独立 sensor actor 的痛点 | 新增 `sensor.camera.rgbd`。一个 actor，两路 capture（RGB + Depth），一次 callback 返回两张子图 |
| 在当前自动驾驶仿真领域快速发展的背景下，ToF 相机作为一种重要的面阵深度感知手段，正日益受到学术界与工业界的高度关注 | `sensor.camera.tof` 是一个新增的 ToF 面阵传感器。第一版只输出点云，后续可补 IR 和 Gray |

## 5. AI 腔句式及其改法

| AI 腔 | 问题 | 改法 |
|------|------|------|
| "具有以下显著优势" | 自夸，没内容 | 删除。直接列能力 |
| "需要指出的是" | 无效铺垫 | 删除，直接说后面的内容 |
| "在 X 的过程中" | 句式松弛 | 改成"X 时"或直接删掉 |
| "通过...实现" | 绕 | 改成主动句："X 调用 Y" |
| "建议在后续版本中..." | 不敢下判断 | "第一版不做 X。目标：..." |
| "需要强调的是" | 强调前先弱化 | 直接说重要的，不预告 |
