DISCUSSION DIGEST / POWERED BY BREACH

讨论很长。
决定在哪里？

看清谁提出了什么，什么改变了判断，
还有什么没定。

跟着一场讨论，找到决定 ↓
THE PROPOSAL

“先用云端搜索。”

→
THE TURNING POINT

“现场没有网络。”

→
THE DECISION

“首版改成本地。”

示意讨论中的一次转折。真正值得保留的，是中间的理由。

01 / MORE THAN A SHORTER THREAD

摘要很短，
却可能漏掉最重要的一句。

一个人提出方案，另一个人补充条件。讨论继续，有人改了主意，有些问题仍然悬着。

如果最后只剩一句“大家决定做本地搜索”，你还是不知道：谁提出了限制，为什么改方案，这个决定管到哪一步。

把讨论的变化留下来。
让结论带着它的来路。
02 / FOLLOW THE DECISION

从“我建议”，到“我们决定”。

示意对话 · 非真实分析结果

案例：团队为一款现场资料工具选择搜索方案。点击三个问题，查看讨论怎样收敛。

SOURCE THREAD / 原始讨论节选
09:10 · 林 / 开发

建议先接云端搜索，索引更新由服务端负责，首版能少做一些同步逻辑。

09:18 · 周 / 开发

我倾向本地索引，不依赖网络。只是更新和容量需要验证。

09:34 · 陈 / 产品

补充现场条件：设备会连续离线两天。首版必须在无网络时也能搜资料。

09:41 · 林 / 开发

那我改为支持本地索引。云端更新可以后补，这次先保证离线搜索。

09:52 · 陈 / 产品

确认：首版本地搜索。周先验证一万份资料的容量与查询耗时，超出范围再讨论。

DISCUSSION DIGEST / 有出处的判断
OPEN QUESTION

分歧在于：
首版依赖云端，还是本地？

林希望减少索引更新的实现工作；周关注无网络时的可用性。此时尚未形成决定。

林 · 立场变化

云端优先

周 · 立场变化

本地优先，待验证容量

此刻不能下的结论

不能把两种建议写成“团队已决定本地搜索”。

09:10 + 09:18 · 林与周

“建议先接云端搜索……” / “我倾向本地索引，不依赖网络。”

示例中的人物、对话和时间均为编写。所有切换在本地完成，不调用模型或读取外部讨论。

03 / A DECISION WITH ITS EDGES

有结论，也有边界。

同一场讨论里，已经决定、仍待验证和接下来要做的事，不能混在一起。

状态这场示意讨论留下的内容依据
已决定首版采用本地搜索，保证离线可用。09:52 明确确认
待验证一万份资料的容量和查询耗时。讨论中没有实测结果
下一步周执行容量与耗时验证。09:52 分配行动
未决定云端更新何时接入。只提出后补，未定时间
04 / SMALL ENOUGH TO TRY

从一条值得读懂的讨论开始。

GitHub issue / PR

沿着提出、质疑和修正，理解方案为什么改变。

邮件与会议讨论

找出明确决定、责任人与仍待补齐的依据。

论坛与社区长帖

保留各方立场；没有共识时，如实呈现分歧。
